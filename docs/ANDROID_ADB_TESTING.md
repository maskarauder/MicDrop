# Android debug APK testing with ADB

The development APK (`com.maskarauder.micdrop.dev`) includes an explicit intent
handler at `com.maskarauder.micdrop.AdbControlActivity`. It uses the normal
visible activity and services, preserving saved pairing and selected devices.
The component requires Android's `DUMP` permission, which the ADB shell holds;
ordinary installed apps cannot invoke it. The release APK has no such component.
The public launcher does not accept these command extras.

## Install and launch

Stop the active stream before replacing the APK so Windows can release its
session. Install with the same signing key to preserve pairing and settings:

```powershell
adb devices
adb install -r .\app-debug.apk
adb shell am start -W -n com.maskarauder.micdrop.dev/com.maskarauder.micdrop.MainActivity
```

Unlock the phone for commands that open the test activity. ADB does not bypass
the lock screen or the microphone/Nearby devices permission prompts. Accept the
normal prompts on first use; Windows pairing approval also remains required.

## Test intents

This PowerShell helper shortens the explicit component name. It does not run a
new shell or change device permissions:

```powershell
function micdrop { adb shell am start -W -n com.maskarauder.micdrop.dev/com.maskarauder.micdrop.AdbControlActivity @args }

# Start using the saved connection and currently selected audio devices.
micdrop --es command connect --es mode playback
micdrop --es command stop
micdrop --es command connect --es mode duplex

# Mute/unmute the active microphone; silence/enable desktop output.
micdrop --es command microphone --ez enabled false
micdrop --es command microphone --ez enabled true
micdrop --es command output --ez enabled false
micdrop --es command output --ez enabled true

micdrop --es command status
micdrop --es command stop
adb logcat -d -s MicDropAdb:I
```

On other shells, substitute the full `adb shell am start -W -n ...` prefix.
`-W` waits for activity launch, not network connection or worker cleanup. Look
for the latest `MicDropAdb` result and the app's session state. Binding/loading
may take up to five seconds. A start action is consumed once; rotation and
returning to the foreground cannot replay it. A new command supersedes an
undispatched command. Commands pending when the activity leaves the foreground
are discarded.

| Command | Extras | Behavior |
| --- | --- | --- |
| `launch` (default) | None | Open the normal app UI |
| `connect` | Optional `--es mode playback`, `microphone` or `duplex` | Start the saved connection; omitted mode uses current options |
| `pair` | `--es invitation <micdrop-link>`, optional mode | Use normal pairing and Windows approval, then normal Connect |
| `stop` | None | Cancel pending pairing/setup or stop the current session |
| `microphone` | `--ez enabled true/false` | Unmute/mute an existing microphone session |
| `output` | `--ez enabled true/false` | Change the existing output control or next-connection option |
| `status` | None | Log fixed phase, saved-connection availability and build |
| `report` | None | Copy the stored stream report to private `no_backup/adb-session-report.txt` |

`connect`/`pair` return `busy_stop_first` if a session is still retained. Wait for
Stop/cleanup before starting another; no replacement offers are generated by the
handler. `requested_check_status` confirms dispatch to the normal connection flow,
not successful playback. Other results include `no_saved_connection`,
`control_unavailable`, `invalid_arguments` and `activity_not_ready`. Detailed
connection outcomes remain in the app/session report. Mode changes update the
next-connection audio/microphone options; device selection stays as chosen in UI.

For first pairing, paste a fresh invitation using a quoted argument:

```powershell
micdrop --es command pair --es mode playback --es invitation 'micdrop://remote/v1/REPLACE_WITH_FRESH_INVITATION'
```

That invitation is a secret: do not include it in shared command transcripts.
The app logs only fixed command/result labels, never intent contents or links.

## Retrieve the report without waking the phone

The debug APK continuously maintains a bounded private report. These commands
work independently of the activity and preserve screen-off testing:

```powershell
adb exec-out run-as com.maskarauder.micdrop.dev cat no_backup/last-stream-report.txt > micdrop-report.txt
adb exec-out run-as com.maskarauder.micdrop.dev cat no_backup/last-java-crash.txt > micdrop-java-crash.txt
```

The crash file exists only after a recorded Java crash. Copy the stream report
before reconnecting, which starts a new report. The explicit `report` command is
optional; after its `report_saved` result, its private copy can likewise be read
with `run-as`. ADB cannot read these private files from a non-debuggable release.

For a controlled handoff, start the saved remote connection, then change Wi-Fi
using the phone's settings. Test audio in both directions, return to Wi-Fi, and
Stop during recovery. USB ADB remains usable while Wi-Fi changes. Wireless ADB
can disconnect when its network disappears. Car/Android Auto handoff and physical
audio continuity still need device testing.

References: [ADB installation and activity-manager commands](https://developer.android.com/tools/adb),
[DUMP permission](https://developer.android.com/reference/android/Manifest.permission#DUMP),
[Android shell permissions](https://android.googlesource.com/platform/frameworks/base/+/refs/heads/main/packages/Shell/AndroidManifest.xml).

## Advanced connection settings

ADB connections use the same saved [Advanced settings](ADVANCED_SETTINGS.md) as
the Connect button. Use `command launch` to open the app, change and save the
connection/recovery settings, then use `command connect`. Settings are captured
at session creation; use Stop followed by Connect after changing them. The
exported report includes requested/effective deadlines and route priorities.
Extended recovery windows require the updated Windows host as well as the APK.
